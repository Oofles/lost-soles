## Description

**Found while working ticket `0118`.** `scripts/copy-maplibre-worker.mjs` runs at `prebuild` and
copies two minified bundles into `public/maplibre/` (ticket `0053`). They are gitignored, correctly —
the whole point is that they stay in lockstep with the `maplibre-gl` pin rather than being vendored.

**Two separate pieces of tooling walk them anyway.**

`eslint.config.mjs`'s `ignores` does not list them, so after any `npm run build`, `npm run lint`
reports **1090 warnings** in two files nobody wrote, and `--max-warnings 0` (D-164) turns that into a
failure:

```
/home/vivicat/lost-soles/public/maplibre/maplibre-gl-shared.js
  5:8558  warning  Expected an assignment or function call ...  @typescript-eslint/no-unused-expressions
... ×1090
```

`scripts/check-design-tokens.mjs` fails on the same two files, and for a reason its own header
argues for rather than against: it **derives its scan roots from disk** on every run, precisely so a
new source directory is covered without anyone remembering to add it (ticket `0142`). `public/` is a
real directory, so the derivation is working exactly as designed — it has simply never been told
which subtree is generated output. It reports a palette leak inside a minified MapLibre bundle.

**CI passes only because of command ordering**, which is the part worth filing. In `amplify.yml` and
in the Actions gate, `npm run lint` runs *before* `npm run build`, so the files do not exist yet when
either tool walks the tree. Reorder those commands — for any reason, by anyone, at any point — and the
build starts failing on vendored third-party minified output. The guard's correctness currently rests
on an unrelated ordering decision, which is the same shape of problem D-164 records about
`--max-warnings 0` and D-163 about a check that runs in only one of two places.

## Acceptance criteria

- [ ] `public/maplibre/**` is in `eslint.config.mjs`'s `ignores`, with a comment saying it is
      generated by `scripts/copy-maplibre-worker.mjs` at `prebuild` and is gitignored.
- [ ] `scripts/check-design-tokens.mjs` skips it too — as a GENERATED-OUTPUT exclusion, named and
      reasoned in the header next to the existing `node_modules` one, not by dropping `public/`.
- [ ] `npm run build && npm run lint && node scripts/check-design-tokens.mjs` passes — the sequence
      that fails today.
- [ ] Both still fail on a real fault in a real source file: a deliberate unused variable for lint,
      a raw hex literal in a component for the token scan. An exclusion written broadly enough to
      blind either check is the failure mode here, not a missing one.

## Steps to reproduce

1. `npm run build` (or just `node scripts/copy-maplibre-worker.mjs`) so `public/maplibre/` exists.
2. `npm run lint`

## Expected vs actual

**Expected:** clean, as it is on a fresh clone.

**Actual:** `✖ 1090 problems (0 errors, 1090 warnings)`, all in
`public/maplibre/maplibre-gl-shared.js` and `public/maplibre/maplibre-gl-worker.js`, and
`--max-warnings 0` makes it exit non-zero. `node scripts/check-design-tokens.mjs` fails on the same
two files with `DESIGN TOKEN VIOLATION — the palette is leaking`.

## Notes

`scripts/**` is already ignored for an unrelated, documented reason (D-160). This is a second entry,
not a change to that one.

Do NOT widen either exclusion to `public/**`. `public/` could one day hold hand-written JS or CSS,
and excluding a directory because today's contents happen to be generated is exactly the
hand-maintained-list failure `check-design-tokens.mjs`'s header argues against at length. The honest
unit is "the directory `copy-maplibre-worker.mjs` writes", which is one path and is already named in
`.gitignore`.

Worth considering while in there, but NOT in scope unless it falls out for free: the general shape of
this bug is "a derived-roots scanner has no notion of generated output". There may be a third tool
with the same blind spot. Filing one is better than widening this.

## Operator validation

None — tooling only. The close is a smoke test: `npm run build && npm run lint` must pass, and lint
must still fail when a deliberate unused variable is added to a source file.
