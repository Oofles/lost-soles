## Description

The first line of application code in the project. A Next.js 15 App Router app plus an Amplify Gen 2
backend definition that deploys, with nothing in it yet but the skeleton
(`01-architecture.md` §1, §5, §6).

Deliverables:

- **Next.js 15, App Router**, TypeScript, `npm`, with `package-lock.json` committed and a `.nvmrc`
  pinning the Node version. `npm run typecheck` (`tsc --noEmit`), `npm run lint` (ESLint, actually
  installed and configured) and `npm test` (vitest) exist as **real** scripts — not the dead-script
  pattern inherited from the existing repo.
- **`amplify/backend.ts`** wiring `defineAuth`, `defineData` and `defineStorage`. Each may be
  near-empty; what matters is that the stack deploys and that later capabilities extend rather than
  introduce them. `0014` fills in the auth configuration.
- **`amplify.yml`** exactly as specified in `01-architecture.md` §6 — a `backend:` phase running
  `npx ampx pipeline-deploy --branch $AWS_BRANCH --app-id $AWS_APP_ID`, and a `frontend:` phase whose
  build runs `npm run typecheck`, `npm run lint`, `npm run build` in that order, with `.next` as the
  artifact base directory and `.next/cache`, `.npm`, `node_modules` cached. `ampx pipeline-deploy`
  must succeed before the frontend build, because it generates the `amplify_outputs.json` that
  `next build` consumes.
- **Amplify Hosting app** connected to `github.com/Oofles/lost-soles`, `main` branch, with
  **deployment skew protection enabled** (GA March 2025, free, zero-config — it prevents 404s when a
  cached bundle requests assets from a superseded deploy). **No WAF** — $15/month per app plus WAF
  charges is roughly 5× the entire D-083 budget, to protect an app with five users behind Cognito.
- **A working local sandbox**: `npx ampx sandbox` deploys a real personal cloud backend, and
  `next dev` on `localhost:3000` reads its `amplify_outputs.json`.

**This is the user's first Amplify Gen 2 backend** (`01-architecture.md` §1). Budget time for the
sandbox/deploy loop being unfamiliar rather than for the code being hard.

**One inherited warning worth heeding** (§6 CI): the existing repo's history (`ed8095b`, `8b4270d`,
`8d97534`) shows repeated failures where **Amplify's clean `npm ci` environment was stricter than
local** — path aliases that resolved locally did not resolve in CI, and an entire `src/layouts`
directory was missing from a commit. Verify every path alias against a clean `npm ci` build and
confirm every new file actually landed in the commit before assuming a deploy will pass.

## Notes

Environments (§6): **local sandbox** (`ampx sandbox`, a real personal cloud backend redeployed on
save), **PR preview** (its own backend stack *and its own secret namespace*, at
`pr-<n>.<app-id>.amplifyapp.com`), and **production** (`main`). There is deliberately **no staging**
environment — at 1–5 users, PR previews with real isolated backends *are* staging, and a third
permanent environment is cost and ceremony for nobody.

Each environment gets its own Cognito user pool, its own DynamoDB tables and its own S3 bucket, so
test data never touches production. Note for later: the sandbox has **no** Strava webhook
subscription, because Strava allows one subscription per application (relevant in capability `14`,
not here).

The custom domain is **not** part of this ticket — 0015 owns it, and it is gated on 0001's pre-flight
audit. Do not let the Amplify console's domain-setup prompt tempt you into claiming the apex.

Depends on 0011 rather than merely 0006 because D-001 gates all implementation on a signed-off,
validated backlog, and 0011 is where the backlog becomes provably valid.

### What went wrong: `npm ci` does not work, and that cost most of the session

The first acceptance criterion was `npm ci && npm run build` from a fresh clone. It fails, and not
because of anything in this scaffold. Reduced to a two-line `package.json`,
`{"@aws-amplify/backend": "^1.24.0"}` alone exits 1 while `{"@aws-amplify/backend-cli": "^1.9.0"}`
alone exits 0. `@aws-amplify/data-construct@1.17.7` and `@aws-amplify/graphql-api-construct@1.22.2`
ship internally inconsistent **bundled** trees — a bundled `@opentelemetry/resources@2.0.0` pinning
`core@2.0.0` beside a bundled `core@2.8.0`. `npm install` tolerates a bundled subtree; `npm ci`
validates it strictly and refuses with ~95 `Missing … from lock file` lines.

Five things were tried and failed, each tested rather than assumed: npm **9.9.3 / 10.5.0 / 10.8.2 /
10.9.2 / 11** (all fail identically, so it is not the local Node 23); `@aws-amplify/backend`
**1.20–1.24** (all fail — every one caret-resolves to the same tarballs); `overrides` on
`@aws-cdk/toolkit-lib`, on `@aws-amplify/plugin-types`, and on `@opentelemetry/core` (an override
rewrites a *specification* and cannot touch the contents of an already-built tarball); pinning both
constructs to their last self-consistent releases, `data-construct@1.17.3` +
`graphql-api-construct@1.21.4`, which made the missing-entry list *longer*; and
`--install-strategy=nested`.

The resolution is **D-162**: both `amplify.yml` phases use `npm install --no-save --cache .npm
--prefer-offline`. Verified from a fresh clone of `main` that it installs from the committed lock,
leaves `package-lock.json` **byte-identical** (md5 `4aa21c50…` before and after), and that
typecheck, lint, test and build all exit 0. The criterion was amended rather than quietly dropped,
and **ticket 0128** carries the revert with a one-minute reproduction to re-test.

What is genuinely lost until 0128 lands: `npm ci`'s guarantee that a build *fails* when
`package.json` and the lockfile have drifted apart. `--no-save` installs from the lock but will not
shout when they disagree. `npm ci || npm install --no-save` was considered and rejected — it would
self-heal silently, which is the opposite of what `npm ci` is for.

The Amplify build image confirmed the diagnosis independently: `nvm use` selected **Node v22.18.0
with npm v10.9.3**, one of the versions tested locally as failing, and the build log contains zero
occurrences of `npm ci`.

Rather than half-create the app, the operator built it in the AWS console, which was the better

**The custom domain was applied at the same time, which is ticket `0015`'s scope, not this one.**
It is correct as applied — `soles.devaultsecurity.com` is `AVAILABLE` and verified, the `soles`
prefix maps to `main`, and neither the apex nor `www` was claimed, exactly as §6 step 5 requires.
Recorded here rather than silently absorbed: **0015 is now substantially done by an out-of-band
action and should be reviewed against its own criteria before being closed.** This ticket claims no
credit for it.

### Deliberate choices worth knowing later

- **`amplify/data/resource.ts` contains a placeholder model, `DeploySmokeTest`.** `defineData`
  refuses an empty schema. It is owner-scoped and nothing should build on it; capabilities 04–06
  replace it.
- **vitest 3, not 4.** vitest 4 crashes npm 10.9.2's dependency resolver outright
  (`Cannot read properties of null (reading 'edgesOut')`) via its `@vitest/browser` → `webdriverio`
  peer chain. Same reasoning as D-155 and D-160: take the option that works with the Node the
  project actually pins.
- **`next-env.d.ts` is committed** even though `create-next-app` gitignores it. `amplify.yml` runs
  `npm run typecheck` *before* `next build`, so in a clean environment the file would not exist yet
  when `tsc` runs. Committing it makes the typecheck deterministic.
- **The existing `.gitignore` from 0004 needed no changes** — it already covered
  `amplify_outputs.json`, `.amplify/`, `node_modules/` and `.next/`.
